    Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-08

    @christianliebel — the mechanical fixes from @jyasskin's review are now committed (squashed into the single commit on this PR).

    For the substantive question this PR raises: what should the charter say about specs that have been in the WG for over a decade without multi-engine implementation?

    Three DAS specs are in this position:

    • Proximity Sensor — first published 12 July 2012. Not shipped in any major browser engine. Mozilla's standards position is negative. No WebKit position filed.
    • Ambient Light Sensor — first published 2 August 2012. Prototyped in Chrome only (behind the #enable-generic-sensor-extra-classes flag since Chrome 67); not shipped in Firefox or Safari.
    • Magnetometer — first published 13 September 2016. Same status: Chrome-only, behind the same flag since Chrome 56; not shipped in Firefox or Safari.

    The WebPerf WG charter sets a useful precedent. It explicitly lists two single-engine specs (Long Tasks API and Device Memory API) with the note: "As this is only implemented in a single browser, we plan to transition this work back to WICG." It also defines re-entry criteria: "Once such WICG-incubated proposal is implemented and available in at least one major browser, and has support from one more, it may be adopted by the Working Group."

    A similar approach here — with explicit re-entry criteria — would signal genuine commitment to multi-engine implementation rather than indefinite maintenance in a WG.

    The TAG concerns in design-reviews#1187 have been re-opened as of this week. The charter needs to either commit to specific milestones for these specs or acknowledge they are single-engine incubations and treat them accordingly.

    Added comment by Jeffrey Yasskin (@jyasskin) at 2026-03-31 (edited in the same day)

    In the TAG review, we wrote:

    We would like the WG to find a way to signal the expected support level for each specification. There's some discomfort on the TAG with using the same spec status—Candidate Recommendation—for all of:

    • deprecated specs that are being maintained while websites migrate to a consensus replacement;
    • features that are stable in one engine but opposed by the others;
    • "living" consensus specs that never intend to advance to Recommendation; and
    • consensus specs that are intended to advance to Recommendation.

    At the same time, we recognize that this is the only status the Process defines for patent protection of these kinds of specifications. At a minimum, each document's support level should be in its SotD section, but ideally the WG would find a way to ensure that developers reading a specification can tell at a glance which kind of document they're reading.

    That's not the same as asking each spec's SotD to describe its current implementation status, and I don't think I want to see an implementation report embedded into the SotDs.

    I would like to request that the WG categorize each spec into something like the above 4 categories, and document that in the SotD. I suspect that we haven't gotten those categories exactly right, and it'd make sense for the WG to discuss exactly what they want to put in the charter.
