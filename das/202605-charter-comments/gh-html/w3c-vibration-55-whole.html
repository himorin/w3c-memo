    "Not enabled by any ports / Tests are skipped by all ports / Unmaintained code"

The problem with the generated format

A new run today via wpt.live would produce the same kind of output as the 2014 snapshot: pass/fail percentages across whatever browsers were tested. That format is designed for checking test conformance. It is not designed to answer the questions W3C Process §6.3.2 requires the Team to consider when assessing adequate implementation experience.

That format doesn't answer any of those questions. A score on a given date doesn't capture that Firefox later removed support entirely on desktop, or that its Android implementation was a stub returning true without performing vibration (Bug 1653318). Regenerating that format now would repeat the same structural limitation.

What an implementation report actually needs to do

The Council Report asked the WG to document what implementation experience the API currently has (verbatim: "document what implementation experience the API currently has (issue 33)"). The Process's §6.3.2 criteria require an authored document that addresses each of those questions — not a snapshot of test pass rates.

PR #55 addresses each §6.3.2 question directly, with a dedicated section for each:

  • Is each feature of the current specification implemented, and how is this demonstrated? — yes, with automated and manual WPT results against the current spec.
  • Are there independent interoperable implementations? — answered honestly: no, single engine (Blink).
  • Are implementations created by people other than the authors? — yes, addressed.
  • Are implementations publicly deployed? — yes, addressed.
  • Are there reports of difficulties or problems? — yes, addressed.

The Geolocation implementation report uses the same structure — a DAS + WebApps joint deliverable published 27 February 2026 for the October 2025 Recommendation. If that is adequate for Geolocation, it is the right model for Vibration.

+    <h2 id="historical">
+      Historical implementation experience
+    </h2>
+    <p>
+      In addition to the current implementation status above, the Vibration
+      API has a history of implementation in engines that no longer support it.
+    </p>
+    <h3>
+      WebKit (EFL port, 2012–2017)
+    </h3>
+    <p>
+      Samsung engineer Kihong Kwon landed initial Vibration API support in
+      WebKit in 2012 for the EFL port, which was used on Samsung Tizen
+      devices. The EFL port enabled the feature
+      (<code>ENABLE_VIBRATION PUBLIC ON</code> in
+      <code>Source/cmake/OptionsEfl.cmake</code>) and received bug fixes
+      through 2015.
+    </p>
+    <p>
+      The EFL port was removed from the WebKit mainline in February 2017.
+      In May 2017, the Vibration API code itself was removed
+      (<a href="https://webkit.org/b/171766">Bug 171766</a>, changeset
+      216696). The removal bug states: "Not enabled by any ports. Tests
+      are skipped by all ports. Unmaintained code."
+    </p>
+    <p>
+      A separate fork,
+      <a href="https://github.com/ewebkit/webkit">ewebkit/webkit</a>,
+      retains the Vibration API code but has not been updated since July 3,
+      2017. The Tizen devices that used EFL WebKit are no longer in
+      production.
+    </p>
+    <p>
+      No Web Platform Test results exist for any EFL WebKit-based browser.
+    </p>
+    <h3>
+      Source code verification (April 2026)
+    </h3>
+    <p>
+      The following was verified by searching and reading the source code
+      of each engine. To reproduce, clone each repository and search for
+      the files and identifiers listed below (e.g., using <code>grep
+      -r</code> or your editor's search).
+    </p>
+    <ul>
+      <li>
+        <strong>Blink</strong>
+        (<a href="https://chromium.googlesource.com/chromium/src/">chromium/src</a>):
+        <code>VibrationController</code> is implemented in
+        <code>third_party/blink/renderer/modules/vibration/vibration_controller.cc</code>.
+        The <code>vibrate()</code> method requires sticky user activation
+        (<code>HasStickyUserActivation()</code>) and blocks calls from
+        cross-origin iframes
+        (<code>IsCrossOriginToNearestMainFrame()</code>) and fenced
+        frames. The WebIDL is in
+        <code>third_party/blink/renderer/modules/vibration/navigator_vibration.idl</code>.
+      </li>
+      <li>
+        <strong>Gecko</strong>
+        (<a href="https://searchfox.org/mozilla-central/source">mozilla-central</a>):
+        The <code>vibrate()</code> WebIDL binding is in
+        <code>dom/webidl/Navigator.webidl</code>, gated on the
+        <code>dom.vibrator.enabled</code> preference. That preference
+        defaults to <code>false</code> in
+        <code>modules/libpref/init/StaticPrefList.yaml</code>.
+        No platform-specific override exists in
+        <code>mobile/android/app/geckoview-prefs.yaml</code> or
+        elsewhere. The HAL implementation remains in
+        <code>hal/android/AndroidHal.cpp</code> (<code>Vibrate()</code>)
+        and <code>hal/fallback/FallbackVibration.cpp</code> (no-op
+        stub for desktop), but is unreachable with the preference
+        disabled.
+      </li>
+      <li>
+        <strong>WebKit</strong>
+        (<a href="https://github.com/WebKit/WebKit">WebKit/WebKit</a>):
+        No <code>vibrate()</code> method in any IDL file. No
+        <code>VibrationController</code>,
+        <code>NavigatorVibration</code>, or <code>ENABLE_VIBRATION</code>
+        flag anywhere in the source tree. The API is entirely absent.
+      </li>
+    </ul>

+    <h2>
+      Is each feature of the current specification implemented, and how is
+      this demonstrated?
+    </h2>
+    <p>
+      All features of [[vibration]] are implemented in the Blink engine (Chrome
+      for Android, Chrome desktop, Edge, and other Chromium-based browsers).
+      This is demonstrated through the automated and manual WPT results above.
+      No other engine provides a functional implementation.
+    </p>
+    <h2>
+      Are there independent interoperable implementations of each feature?
+    </h2>
+    <p>
+      <strong>No.</strong> Only one browser engine (Blink) provides a
+      functional implementation. Firefox removed support in version 129
+      (August 6, 2024); the API is now disabled on all Firefox platforms,
+      including Android (see <a href="#historical">Historical
+      implementation experience</a>). WebKit has never shipped the API
+      and formally opposes it.
+    </p>
+    <h2>
+      Are the implementations by different, independent developers?
+    </h2>
+    <p>
+      The Chromium-based implementations (Chrome, Edge, Opera, Samsung
+      Internet, etc.) share the same Blink engine codebase and are not
+      independent of each other. They represent a single implementation.
+    </p>
+    <h2>
+      Are the implementations deployed on production systems?
+    </h2>
+    <p>
+      Yes, in Chromium-based browsers. Not in Firefox (removed) or Safari
+      (never shipped).
+    </p>
+    <h2>
+      Are there reports of difficulties or problems with implementation?
+    </h2>
+    <p>
+      Yes. Chrome introduced cross-origin iframe restrictions (v55) and user
+      gesture requirements (v60) in response to widespread abuse of the API.
+      A <a href="https://github.com/w3c/vibration/issues/33">manual review
+      of sites calling <code>navigator.vibrate()</code></a> found usage
+      dominated by notification emulation, ad-related scripts, and patterns
