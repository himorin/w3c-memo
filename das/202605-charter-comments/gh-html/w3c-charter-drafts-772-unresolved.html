Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-08

WebKit's published position on the WebUSB API is oppose. The rationale: "This spec also depends on a specific hardware technology, and enables dependency on specific attached hardware accessories, which risks the device independence of the web" — alongside security and privacy concerns.

Worth noting that these concerns are not equivalent. The security concern is potentially addressable through permission model changes. The device-independence concern is structural: an application built to communicate with a specific USB device will only work on devices with that hardware attached. That's not addressable by changing the permission dialog.

Adding WebUSB as a tentative deliverable implies a path to Recommendation, and the W3C Process asks whether "there are independent interoperable implementations of the current specification" before a spec advances. These APIs also face portability constraints on platforms where USB access is mediated by the OS rather than exposed directly to applications.

What has changed in the API's design or permission model since the WICG incubation that would make this appropriate to advance through DAS?

Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-12

@reillyeon You're right that device-independence doesn't mean "every web app must work on every device." The web already has APIs that only work with specific hardware (Gamepad, Geolocation). The Design Principles §1.6 explicitly say "this doesn't imply that features which don't work in every possible context should be excluded." I agree.

The concern is about the level of abstraction, not the existence of hardware-specific apps. Consider Gamepad vs. WebUSB:

Gamepad API WebUSB
Abstraction Capability: buttons[0].pressed Transport: transferOut(endpoint, bytes)
Compatibility Any gamepad, normalized via mapping: "standard" One specific vendorId:productId
Who writes the driver Browser vendor Web developer, in JavaScript

The Gamepad API abstracts hardware: write gamepad.buttons[0].pressed and it works across Xbox, PlayStation, Switch Pro, and generic HID controllers. WebUSB exposes raw USB transfers where the developer must parse byte buffers and implement the device protocol themselves. Every WebUSB app is effectively a bespoke USB driver. The most-used projects on GitHub confirm this: arduino, webadb, fastboot.js, webdfu, webminidisc. Each targets a single device or protocol.

This also affects portability: on platforms where USB access is mediated by the OS (iOS, iPadOS), WebUSB can't be implemented. The Gamepad API doesn't have this problem because the browser reads HID reports through the OS's existing gamepad stack.

As annevk noted on WebKit/standards-positions#68: "if the details of the connection are sufficiently abstracted such that they can change over time, there might be a way forward there."

A constructive path: those GitHub projects cluster around a few use cases: firmware updates, debug bridges, device configuration. Could the WG explore purpose-built APIs for those categories rather than standardizing raw USB access? The existing ecosystem is essentially telling us what the right abstractions would be.

More broadly: the web platform generally works at the level of capabilities (audio, video, input, storage), not hardware buses and wire protocols. Is there a reason USB warrants a different approach?

Comment by Reilly Grant (@reillyeon) at 2026-04-14

Gamepad API abstracts hardware

This is possible because "gamepad" is a category of device for which an abstraction already exists, similar to Keyboard Events or Pointer Events. The purpose of lower-level APIs such as WebUSB is to support devices for which no broadly-available abstraction yet exists. It is more similar to the Fetch API, which allows a site to make arbitrary (within limits) HTTP requests without requiring that the API provided by the server implements any kind of higher-level abstraction. The site must parse and interpret the JSON or XML response itself. There is no "Web Weather API" which provides a higher-level interface to a REST service providing meteorological forecasts.

[...]on platforms where USB access is mediated by the OS (iOS, iPadOS), WebUSB can't be implemented.

I don't consider this an implementation barrier as if Apple wanted to implement this API on iOS/iPadOS it could make the necessary changes (if any) to the OS as Google has done to enable browsers to implement WebUSB on Android and ChromeOS. The existence of a WebUSB implementation for macOS implies that it is possible on other Apple platforms.

An alternative path: if Apple's concern is building specific APIs for low-level transports such as USB, serial or Bluetooth I could see an alternative proposal, in the spirit of WebTransport, which specified a high-level bidirectional transport which could be implemented on top of these low-level protocols. The challenge for this approach and the reason it was rejected in favor of the existing proposals is that this would require buy-in from every hardware manufacturer to modify their device firmware or design the devices for this API from the beginning. An important benefit of WebUSB and related APIs which has been observed from their adoption is that it allows developers to build software for existing devices without the permission of the manufacturer.

Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-14

The Fetch analogy is interesting but I think it highlights the difference rather than closing it. A Fetch-based app depends on a server API, which is accessible from any networked platform via a standardized protocol. A WebUSB-based app depends on a specific attached hardware accessory using a vendor-specific device protocol. The first is a software dependency; the second is a hardware dependency. That distinction is what the WebKit position means by "enables dependency on specific attached hardware accessories, which risks the device independence of the web."

On iOS: the web's portability in practice comes from building on what platforms already provide, not from requiring platforms to change their security models. "Apple could make the necessary changes" is true of any API on any platform, which is why it doesn't resolve the portability concern.

Your alternative path proposal (a high-level bidirectional transport in the spirit of WebTransport) is the most interesting part of this thread to me. The manufacturer buy-in concern is real, but this is exactly the kind of question the charter should address: whether DAS pursues raw transport standardization or use-case abstractions. A tentative deliverable for WebUSB as-is already commits to one side of that question.
