Initial comment by Marcos Cáceres (@marcoscaceres) at 2026-03-31 (edited in 2026-05-12)

Context: This issue tracks a concern raised in the TAG review of the 2026 DAS WG charter (w3ctag/design-reviews#1187).

The TAG review states (charter-affecting section, verbatim):

"We're concerned by the appearance of Web Serial in the Tentative Deliverables. At least Mozilla seems inclined to start implementing that API, and we want it to live in a WG that all implementers are comfortable joining, to ensure that all of their potential concerns about engine/platform capabilities, privacy, and security can be easily raised. That said, its presence in this charter doesn't prevent it from being adopted by another WG instead."

Issue #771 proposes moving Web Serial from Tentative Deliverable to full Deliverable based on Mozilla's intent to prototype. However, the TAG's concern is specifically about venue — which WG is the right home for this work — not solely about the number of implementations. Moving it to a full DAS deliverable without resolving the venue question does not address the TAG's concern; it reinforces it.

Before this charter proceeds to AC review, the charter should either:

  1. Document that the venue question has been discussed with the Web Applications WG and record the outcome, or
  2. Explicitly state that Web Serial will not advance to full Deliverable in DAS until the venue question is resolved, and commit to a process and timeline for making that decision.

Related: #770, #771, w3ctag/design-reviews#1187

On the substance: venue matters for eventual implementer engagement on Recommendation track. WebKit's position on Web Serial is under evaluation (WebKit/standards-positions#199). One open question is whether Web Serial has the same device-independence profile as WebUSB and Web Bluetooth — serial communication may be less hardware-specific, but the same structural question applies: does the API enable applications that only work on devices with specific serial peripherals attached?

@tantek — Mozilla has an intent to prototype Web Serial. What is Mozilla's view on DAS as the venue, given the note already in the charter that "this work may turn into a joint deliverable with the Web Applications Working Group"?

Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-16

Following up on my question to @tantek about Mozilla's preferred venue: Mozilla has filed a WHATWG Steering Group workstream proposal covering Web Serial alongside USB, HID, Bluetooth, and NFC — whatwg/sg#264. That appears to be Mozilla's answer to the venue question this issue raises.

Worth noting for the group: the WHATWG workstream policy requires proposed standards to be "likely to be implemented by the major browser engine developers"... that's the same multi-implementer question this issue is trying to resolve. The WHATWG's SG process will need to address that.

Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-30

Posting as W3C Member (not TAG Member).

Update: WebKit's published position on Web Serial (standards-positions#199) includes a venue analysis. The position notes that Web Serial has been in WICG incubation for approximately 12 years and remains implemented only in Chromium. It argues that graduating from incubation should happen when there is a credible path to multi-engine implementation, and that no additional browser engine has committed to implementing this API.

The position also cites the Web Performance Working Group's updated charter as a precedent: that charter transitions single-engine specifications (Long Tasks, Device Memory) back to WICG incubation and requires proposals to be "implemented and available in at least one major browser, and [have] support from one more" before the WG adopts them.

This is consistent with the concern this issue raises.
