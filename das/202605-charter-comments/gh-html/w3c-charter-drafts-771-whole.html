Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-08

Before integrating this, a few things worth noting while the charter is still in the refinement phase (In Charter Refinement) and horizontal reviews are ongoing — including an unresolved i18n issue (i18n-needs-resolution on w3c/strategy#530).

Mozilla's intent to prototype is noted, but an intent is not yet an implementation. Promoting Web Serial from tentative deliverable to full deliverable implies the WG expects this to proceed to Recommendation, which the W3C Process says requires the Team to consider whether "there are independent interoperable implementations of the current specification."

The request doesn't explain what use cases or platform-model changes make this appropriate to promote now that weren't present during the WICG incubation. What is different? WebKit's position on Web Serial is under evaluation (WebKit/standards-positions#199), and it's an open question whether Web Serial has the same device-independence profile as WebUSB and Web Bluetooth.

The venue question in #783 is also directly relevant and unresolved.

Comment by Marcos Cáceres (@marcoscaceres) at 2026-04-30

Posting as W3C Member (not TAG Member).

Update: WebKit has published a position on Web Serial — standards-positions#199. The position is oppose, citing device independence, privacy, security, use cases, and venue concerns.

Additionally, peer-reviewed research published since my last comment identifies concrete Web Serial threats. "Peripheral Instinct: How External Devices Breach Browser Sandboxes" (Trampert et al., CISPA/Universität des Saarlandes; WWW '25) describes "several potential threats that can be exploited by a malicious actor that can control a modem via the Web Serial API," including premium-rate dialing/SMS, interception of 2FA codes via SMS forwarding, GPS tracking, and permanent SIM card lockout. I've filed a separate charter issue with the full findings: #798.
