Comment by Marcos Cáceres (@marcoscaceres) at 2026-03-03 (edited in 2026-03-12)

Thanks for the updates, @reillyeon. The clearer implementation status and expected progress sections are a meaningful improvement. Thank you for the work on this.

Stepping back, however, I think there remain several structural gaps that prevent the charter from fully addressing the TAG review and Council recommendations.

1. Trajectory clarity for single-engine specifications

For Generic Sensor and Compute Pressure, the charter signals continued evolution but does not define:

  • The interoperability objective during this charter;
  • The expected timeline for achieving multi-engine support;
  • Or what happens if sustained barriers remain.

Without explicit criteria or review checkpoints, CR risks becoming an open-ended resting state rather than a convergence mechanism. Clarifying the validation and reassessment model would go a long way toward addressing the TAG’s signaling concerns.

Additionally, it would be helpful to explicitly commit that specifications with limited implementation support will clearly reflect that status in their Status of This Document (or similar prominent signaling). Developers read the specification itself, not the charter, and support level and intended trajectory should be visible there as well.

2. Vibration and scope/coordination with Web Apps

The Vibration text now references evolving toward “device haptics capabilities.” However, haptics are explicitly in scope of the Web Applications WG, which also has an incubated Haptics proposal.

If the intent is to:

  • Maintain Vibration as a minimal primitive, that should be stated.
  • Expand toward richer haptics capabilities, explicit coordination or a joint deliverable model with Web Apps would seem necessary.

As written, the abstraction boundary and coordination model are unclear.

3. Response to the Council recommendation (Vibration in particular)

The Council asked the WG to document the plan it believes is best, including rationale. The current charter text signals ongoing maintenance but does not clearly articulate:

  • Whether the WG has re-evaluated the API’s continued fitness for purpose;
  • What criteria would lead to redesign, transition, or discontinuation;
  • Or what the long-term trajectory is during this charter.

Making that plan explicit would close the loop cleanly.

I’m raising these points constructively and would be happy to help draft language that tightens these areas. The improvements so far are appreciated; I think we’re close, but these structural clarifications would make the charter clearly responsive and reduce the likelihood of objections later.

Comment by Marcos Cáceres (@marcoscaceres) at 2026-03-31

Thanks for the work on this PR. To make it possible for me to approve, here are concrete text suggestions for the sections that need changes, along with tracking issues for anything that can't be resolved in this PR alone.

Suggested charter text

1. Add to the Deliverables preamble or Success Criteria section
(Addresses TAG concern: developer SotD signaling; source: w3ctag/design-reviews#1187)

The Working Group will ensure that each specification clearly communicates both its implementation status and its intended trajectory along the W3C Recommendation Track. At a minimum, the Status of This Document section of each specification will describe the current level of implementation support and whether the specification is expected to advance toward widely implemented Recommendation status.

For specifications with limited or single-engine deployment, the specification will clearly signal its role and intended direction — for example, whether it is an experimental abstraction, a transitional design pointing developers toward a consensus alternative, or work with limited deployment serving as documentation.

The Working Group will review specifications with limited implementation support at least annually, document the outcomes publicly, and adjust the trajectory of each deliverable accordingly.

Tracked in: #780

2. Vibration — replace current "Expected progress" text
(Addresses TAG concern + Council recommendation; sources: w3ctag/design-reviews#1187, https://www.w3.org/2025/08/vibration2-council-report.html#recommendations)

Current text: "The Working Group will update the specification to modern web platform design principles and device haptics capabilities and continue to solicit feedback."

Suggested replacement:

Before this charter proceeds to AC review, the Working Group will publish a document describing its plan for the Vibration API — including its rationale and the criteria it will use to evaluate whether to continue, redesign, or transition this work — as recommended by the W3C Council (https://www.w3.org/2025/08/vibration2-council-report.html#recommendations). The Working Group will also update the implementation report (w3c/vibration#33) to accurately reflect current browser support. Any work touching haptics capabilities will be conducted in coordination with the Web Applications Working Group.

Tracked in: #781, #782

3. Proximity Sensor and Ambient Light — replace vague "Expected progress" text
(Personal concern: no actionable plan or timeline)

Current text (both): "The Working Group will continue to collect feedback from the community on the use cases for this API and may publish a new Working Draft."

Suggested replacement:

The Working Group will proactively seek published implementer positions from browser engines not currently participating in the WG. By [WG to specify date], the Working Group will publish a summary of responses — including any non-responses — and use these to inform a decision on whether to continue, redesign, or discontinue this work on the Recommendation track. The Working Group will document that decision publicly.

4. Generic Sensor — replace "infrastructure for future sensor APIs"
(Personal concern: the framing conflicts with the TAG's stated skepticism about the Generic Sensor architecture in future design reviews; source: w3ctag/design-reviews#1187)

Current text: "The Working Group will continue to maintain the specification as infrastructure for future sensor APIs."

Suggested replacement:

The Working Group will continue to maintain the specification. The Working Group will not charter new Generic Sensor-derived deliverables without first documenting the architectural rationale relative to single-layer API alternatives.

Tracking issues filed

The following issues track the concerns that need to be resolved before AC review, whether in this PR or separately:

  • #780 — Charter must commit to SotD signaling (TAG concern)
  • #781 — Vibration: Council-recommended plan must be published before AC review (Council + TAG concern)
  • #782 — Vibration: "device haptics capabilities" scope conflict with WebApps WG
  • #783 — Web Serial: resolve TAG's venue concern before AC review (TAG concern)

Once suggestions 1 and 2 above are incorporated and issues #781 and #783 have a clear path to resolution before AC review, I'm happy to update my review.

The Working Group will ensure that each specification clearly communicates both its implementation status and its intended trajectory along the W3C Recommendation Track.
