Concerns raised by the TAG

At 2026-02-12 (UTC), TAG member Christian Liebel raised five concerns, with additional concerns which don't affect the charter but the TAG want to flag a few issues. At 2026-05-07 (UTC), Christian Liebal again confirmed to be sure to specifically address the first 5 bullet points by TAG consensus.

5 points of concerns

The TAG endorses work on device APIs and the effort to get patent protection even for single-engine features, but we have several concerns with the way the DAS WG is being chartered to do that.

  • We're concerned to see the Chromium-only Accelerometer, Gyroscope, and Orientation Sensor specifications in the charter, now that the Device Orientation and Motion spec is in Baseline. It makes sense to maintain non-consensus specifications while websites switch over to equivalent consensus APIs, but the charter should commit to only adding new features to the consensus versions. If there's not enough consensus on the new features to incorporate them into the core Device Orientation and Motion spec, this WG could develop an extension specification that allows websites to mostly use the Baseline feature, with a few engine-specific extensions.

  • We want to ensure that the other specifications fill clear user needs and are making appropriate tradeoffs between those user needs and any potential abuse of the APIs. In many WGs, we can rely on all 3 browser engines to check this, but since this WG does not currently include participation from all major browser engines, we're more concerned here. Could you add this goal to the charter for each of the specifications in that class? We see, for example, Create an explainer w3c/vibration#45 to do this for Vibration, but it would be good to use the charter to ensure it gets done.

  • The Vibration Council recommended that "the WG document the plan [to ship in multiple major browser engines] it thinks is best, whether or not that plan includes implementation in multiple browser engines, and a compelling rationale to help any reviewers decide whether the plan is acceptable." We couldn't find such a plan in this rechartering effort, and we encourage the WG to write such plans for each single-engine specification, in order to head off this possible formal objection.

  • We would like the WG to find a way to signal the expected support level for each specification. There's some discomfort on the TAG with using the same spec status—Candidate Recommendation—for all of:

    • deprecated specs that are being maintained while websites migrate to a consensus replacement;
    • features that are stable in one engine but opposed by the others;
    • "living" consensus specs that never intend to advance to Recommendation; and
    • consensus specs that are intended to advance to Recommendation.

    At the same time, we recognize that this is the only status the Process defines for patent protection of these kinds of specifications. At a minimum, each document's support level should be in its SotD section, but ideally the WG would find a way to ensure that developers reading a specification can tell at a glance which kind of document they're reading.

  • We're concerned by the appearance of Web Serial in the Tentative Deliverables. At least Mozilla seems inclined to start implementing that API, and we want it to live in a WG that all implementers are comfortable joining, to ensure that all of their potential concerns about engine/platform capabilities, privacy, and security can be easily raised. That said, its presence in this charter doesn't prevent it from being adopted by another WG instead.

Additional concerns not affect the charter

The following concerns don't affect the charter, but we want to flag a few issues that are likely to come up in future design reviews for the individual specifications:

  • We will always look more critically at specifications developed by WGs without members from all major browser engines, since we want there to be One Web in the long run, and the fact that some browsers decide not to implement, inherently means there are concerns with the design. The WG should be prepared to explain how the non-members' critical feedback has been sought and considered.
  • The Generic Sensor architecture seems overcomplicated overall. In reviews of features that use it, we'd appreciate some justification for why that architecture is better than defining APIs in a single layer, as Device Orientation and Motion does.
  • Are the signals in the Battery API still the right ones to help websites help users achieve their goals? Would a "please reduce power use" signal be sufficient, with the UA in charge of deciding how the precise battery level and charging state contribute to that signal?

Comment by Marcos Cáceres at 2025-03-18 (UTC) (edited in the same date)

Following up on my earlier comment, I think this might be pointing at a broader issue than just adding these specs to DAS.

Right now, I’m trying to understand what has changed in the world to support including these specs in DAS.

Historically, there has been fairly strong alignment across WebKit, Mozilla, and the TAG that this class of APIs has unresolved concerns, particularly around permission and enablement models, as well as fingerprinting:

  • Mozilla has said "only rely on user consent … is not sufficient"
  • WebKit has not implemented Web Bluetooth, Web NFC, or Serial due to "fingerprinting, security, and other concerns"
  • TAG discussions continue to raise issues with the model itself, for example "permission fatigue" and "serialNumbers are awfully unique"

Given that, it would be helpful to clarify:

👉 What has changed, either in the underlying enablement or permission model, or in Mozilla’s position(s), that makes these APIs appropriate to include in DAS?

Right now, it is not obvious what new alignment or architectural progress the W3C would be acting on.

At the same time, this raises a governance question. TAG has already highlighted concerns where there is not participation from all major browser engines and asked for plans in those cases (feedback).

In practice here, different engines are exploring different models, key architectural questions remain open, and WebKit is not participating due to those concerns. It’s hard to see how we get to interoperable outcomes if we do not first agree on the model we are trying to standardize.

Taking these APIs wholesale into a Working Group under those conditions risks assuming the model is already good enough and pushing alignment problems downstream. For APIs with long-standing concerns, implementer interest alone does not seem like a sufficient bar.

More importantly, this points to a limitation in the current governance model. DAS does not appear well suited for standardizing APIs where the model is still under debate and multi-engine participation is not yet established.

A possible path forward could be to first clarify what has changed, re-establish alignment at the architectural level with TAG involvement, and consider whether this work needs a venue or process explicitly designed for early cross-engine collaboration before taking specs wholesale into standardization.

To be clear, I’m supportive of making progress here, but it feels like we need to align on both the model and the governance approach first across implementers, the TAG, and the W3C community at large.

@reillyeon You're right that device-independence doesn't mean "every web app must work on every device." The web already has APIs that only work with specific hardware (Gamepad, Geolocation). The concern is about the level of abstraction, not the existence of hardware-specific apps. Consider Gamepad vs. WebUSB:

Gamepad API WebUSB
Abstraction Capability: buttons[0].pressed Transport: transferOut(endpoint, bytes)
Compatibility Any gamepad, normalized via mapping: "standard" One specific vendorId:productId
Who writes the driver Browser vendor Web developer, in JavaScript

The Gamepad API abstracts hardware: write gamepad.buttons[0].pressed and it works across Xbox, PlayStation, Switch Pro, and generic HID controllers. WebUSB exposes raw USB transfers where the developer must parse byte buffers and implement the device protocol themselves. Every WebUSB app is effectively a bespoke USB driver. The most-used projects on GitHub confirm this: arduino, webadb, fastboot.js, webdfu, webminidisc. Each targets a single device or protocol.

This also affects portability: on platforms where USB access is mediated by the OS (iOS, iPadOS), WebUSB can't be implemented. The Gamepad API doesn't have this problem because the browser reads HID reports through the OS's existing gamepad stack.

As annevk noted on WebKit/standards-positions#68: "if the details of the connection are sufficiently abstracted such that they can change over time, there might be a way forward there."

A constructive path: those GitHub projects cluster around a few use cases: firmware updates, debug bridges, device configuration. Could the WG explore purpose-built APIs for those categories rather than standardizing raw USB access? The existing ecosystem is essentially telling us what the right abstractions would be.

More broadly: the web platform generally works at the level of capabilities (audio, video, input, storage), not hardware buses and wire protocols. Is there a reason USB warrants a different approach?

Continuing the discussion from #772, the exception to this for some APIs is the iOS platform, where Apple has made the product decision to block applications from implementing Web Serial, WebHID and WebUSB, however the hardware itself is perfectly capable of supporting such an implementation. This is demonstrated by the fact that the Macbook Neo is based on the same SoC as the iPhone 16 Pro and Chromium's implementations of these APIs work perfectly fine there.
